# Context model

Use this reference to frame the product situation before evaluating an interface.

## Establish the decision context

1. Name one primary request mode: guide, scan, refactor, or verify.
2. Select one registered scenario family. Do not invent a nearby alias.
3. Identify the task, entry state, intended outcome, environment, channel, and time boundary.
4. Identify the acting party, affected parties, decision owner, and operational owner.
5. State which evidence capabilities are actually available: page or content, runtime, code, component contract, or research.
6. Record missing inputs as unknown. Do not convert missing evidence into a pass, a failure, or a product claim.

## Keep scenario differences material

Evaluate an Admin workflow through operational safety, permissions, recovery, density, and repeated-use costs. Evaluate a public website through information scent, comprehension, navigation, accessibility, and read-only task completion. Evaluate a transaction through price, commitment, error recovery, and effect boundaries. Evaluate cross-channel work through handoffs and state continuity.

Do not transfer a conclusion from one scenario family to another without assessed evidence. Do not aggregate heterogeneous sites into a total UX score or ranking.

## Define observable success

Express success as an observable task state, not an aesthetic preference. Bind each observation to its source artifact, actor, environment, and time scope. Treat a famous brand, a polished visual style, an automated scan, or zero Findings as insufficient evidence of user success.

Use the canonical registries and schemas for exact identifiers, fields, and collection rules. This reference supplies procedure, not an alternate data model.
