# Risk reporting

Use this reference to report assurance and uncertainty as separate, traceable outputs.

## Build the assurance track

1. Link each Finding to the exact rule evaluation, source material, affected context, and reason code.
2. Describe the observable condition before describing its possible consequence.
3. Assess likelihood, impact, affected parties, reversibility, detectability, and uncertainty from available evidence.
4. Distinguish current harm, credible risk, implementation gap, and unsupported concern.
5. Carry release-critical unknowns into escalation rather than silently lowering severity.
6. State residual conditions and the owner responsible for resolving them.

Do not claim that zero Findings means the experience is good, accessible, safe, or complete. Do not use an automated scan as proof of WCAG conformance. Do not increase severity because a target is famous or decrease it because a component library is reputable.

## Build the inquiry track

Place unverified explanations, user-outcome questions, and research needs in Inquiry. Keep them out of Findings, authorization, and release gates until assessed evidence exists.

## Recommend within ceilings

Offer alternatives before selecting one. Bind each recommendation to assessed claims, authority material, risk, and reversibility. Use the weakest strength allowed by all ceilings. Preserve required actions only when exact normative entailment exists.

Report release as allow, allow with verified executable conditions, undecided, escalation, block, or no release according to canonical policy. Include scope, evidence limits, unresolved risks, and the next decision owner. Never output a hidden total UX score or cross-site ranking.
